# FEEDBACK — SEDEFI-176 Independent Solution

DevX evaluation of the DeepBook sandbox + surrounding stack (Sui SDK 2.x, DeepBook v3, dapp-kit-react, Move 2024, sui-pilot bundled docs), captured continuously across six build cycles that produced three apps under `independent/`:

- **Slot 1** — Public market-stats SPA (React + Vite, no wallet, ~1257 LOC TS).
- **Slot 2** — Slippage-protected single-hop swap (Move 2024 module + tests, ~150 LOC).
- **Slot 3** — TP/SL vault: Move package + Node.js keeper + React + dapp-kit-react UI (~700 LOC TS+TSX, ~160 LOC Move, ~600 LOC keeper TS).

Every bullet below cites the `independent/raw-friction.log` line that backs it, by ISO timestamp + source tag, per the spec's source-attribution discipline. `[forge-process]` entries from the friction log are excluded unless they surface a DeepBook-relevant issue, in which case they're re-tagged.

The three sections required by the Linear ticket are §1 (working well), §2 (can be improved), §3 (not working / needs fix or refactoring).

---

## 1. What is working well

- **Move 2024 + DeepBook v3 no-manager swap is genuinely clean** (`raw-friction.log` 2026-04-27T23:55:00Z, `[deepbook]`). `deepbook::pool::swap_exact_base_for_quote` (no-manager path, lines 248-266 of `pool.move`) takes `(pool, base_in, deep_in, min_quote_out, clock, ctx)` and returns the three output coins as a tuple. Slot 2's wrapper module is 54 source LOC including doc comments — the DeepBook surface required no plumbing object, no BalanceManager, no PTB orchestration, just a function call wrapped in an `assert!`. Setting `min_quote_out = 0` on the inner call to delegate slippage assertion to the wrapper is a clean composition primitive: it lets the wrapper own the abort code without DeepBook fighting it. This is the platonic ideal of a Sui Move dependency.

- **`pnpm deploy-all` end-to-end orchestration is high-leverage when it works** (`raw-friction.log` 2026-04-27T20:55:00Z, `[sandbox]`). Single command brings up 8 containers (Sui localnet, indexer, server, postgres, faucet, oracle, market maker, dashboard), publishes ~7 Move packages, creates 2 pools, writes a usable manifest at `sandbox/deployments/localnet.json`, and auto-opens the dashboard. When the bootstrap succeeds (and after the `down -v` workaround is internalised), iteration on consumer apps becomes very fast — the manifest layer alone removed every "what's the package id" question across all three apps. The architectural ambition is exactly right; the gaps documented in §3 are gaps within a sound design.

- **sui-pilot bundled docs were load-bearing for Move 2024 and Sui SDK 2.0 migration** (`raw-friction.log` 2026-04-27T22:55:00Z, `[sui-sdk]`). The `.ts-sdk-docs/sui/migrations/sui-2.0/sui.mdx` and `.move-book-docs/book/programmability/` corpora caught multiple stale-training-memory pitfalls that would otherwise have produced runtime-broken-but-compiles code: the Sui SDK 2.x `Transaction#build({client})` resolution-client requirement, the dapp-kit `dAppKit` prop name (was `client` in 1.x), the `keypair.sign` return-type change. Without these docs, every Sui-SDK-touching cycle would have needed a discovery pass against the npm package source. Sui Move evolves fast enough that the bundled-doc-first rule the agent operates under is the right default.

- **Move's resource model + atomicity made Slot 3 (TP/SL vault) straightforward to reason about** (`raw-friction.log` 2026-04-28T00:30:00Z, `[move]`). The `Vault<T>` shared object holding a `Balance<T>` is a textbook escrow pattern; the permissionless-but-condition-gated `execute_trigger` entry composes naturally with DeepBook's `swap_exact_base_for_quote` because both the swap and the post-swap routing live in the same transaction. There was no need for a "request-then-execute" two-phase pattern, no need for an off-chain settlement layer, and the test scaffolding (`deepbook::pool_tests::setup_everything<SUI, USDC, SUI, DEEP>`) Just Worked once the per-test-scenario lifetime was understood. Compared to writing the same thing on EVM, the Move version was about half the lines and far easier to verify by reading.

- **Sui SDK 2.x raw-fetch JSON-RPC bypass is a viable escape hatch** (`raw-friction.log` 2026-04-27T21:47:00Z, `[sui-sdk]`). All three TS apps use direct `fetch` against `http://127.0.0.1:9000` for `suix_queryEvents` / `sui_getObject` / `sui_devInspectTransactionBlock` rather than the typed `SuiClient`. This was originally a Slot-1 expedient (the typed client's BigVector traversal was awkward), but it became the consistent pattern across keeper + UI because the typed client's overhead — schema generation, response parsing, retry semantics — was net-negative for short-lived poll loops. The fact that the SDK doesn't fight you when you go around it is itself a plus.

- **Move test_scenario `setup_everything` fixture from DeepBook is a reusable testing primitive** (`raw-friction.log` 2026-04-27T23:55:00Z, `[deepbook]`). Slot 3's seven unit tests all start from `deepbook::pool_tests::setup_everything<SUI, USDC, SUI, DEEP>` — one line gives you a published DeepBook package, a registered pool, a balance manager, and the requisite Pyth oracle objects in the test VM. Writing the equivalent ad-hoc fixture would have been ~100 LOC per test file; reusing the bundled one made the Vault tests focus exclusively on Vault logic.

## 2. What can be improved

- **Sui SDK 2.x signing/building/executing API surface is fragmented across multiple iterations to land** (`raw-friction.log` 2026-04-27T22:55:00Z, `[sui-sdk]` and Cycle 4 review). Building a signed-and-executed transaction against `@mysten/sui ^2.14` requires composing `Ed25519Keypair.fromSecretKey` (or `.generate()`) → `Transaction#build({ client })` → `keypair.sign(bytes)` → `executeTransactionBlock(signedTx)`, with the `client` argument required by `build()` needing a real `SuiClient` that supports `multiGetObjects` — passing `undefined as never` as a cast (Cycle 4 iter-1) compiles cleanly and fails at runtime. The migration guide at `.ts-sdk-docs/sui/migrations/sui-2.0/sui.mdx` shows individual primitives but not the resolution-client coupling. Recommendation: add a one-page "submit a signed PTB end to end" recipe to the migration docs, with an explicit note about which `SuiClient` methods `build({ client })` calls under the hood.

- **`Transaction#serialize()` deprecation has no SDK-blessed structural-inspection alternative** (`raw-friction.log` Cycle 4 review carry-forward, `[sui-sdk]`). The method is marked deprecated, but `tx.toJSON()` requires resolved object refs and therefore an RPC round-trip. There is no in-memory way to inspect a built PTB's command list for a unit test that doesn't want to stand up a fake `SuiClient`. Slot 3's keeper tests work around this by spying on `fetch` itself, which couples the test to the JSON-RPC wire format rather than to the SDK's transaction model. Recommendation: ship a stable structural representation (`tx.getInputs()`, `tx.getCommands()`) that doesn't need RPC resolution.

- **`suix_queryEvents` JSON-RPC params are positional and undocumented** (`raw-friction.log` Cycle 4 review, `[sui-sdk]`). The transport layer at `@mysten/sui` 2.16 `client.mjs:413` shows `[query, cursor, limit, descending: bool]`, but neither `.ts-sdk-docs/` nor any module docstring documents this. Cycle 4 iter-1 swapped the order and the keeper silently never discovered any vault — every test still passed because the test seam stubbed the response. Recommendation: surface the param order (or a typed RPC binding) in the SDK's published types, not just the implementation.

- **dapp-kit-react ^2.0.1's `DAppKitProvider` prop is `dAppKit`, not `client`** (`raw-friction.log` Cycle 5 review, `[dapp-kit]`). The 2.0 migration kept the provider name but renamed the prop. Without reading `.ts-sdk-docs/sui/migrations/sui-2.0/dapp-kit.mdx` first, the natural guess is wrong and the error is a generic React render error rather than a clear "wrong prop name" message. Recommendation: deprecate the old prop name with a runtime warning for one minor version before removing it.

- **`InMemorySignerAdapter` lives in the `@mysten-incubation/dev-wallet/adapters` namespace** (`raw-friction.log` Cycle 5 review, `[dapp-kit]`). The incubation namespace is unexpected (the rest of the dapp-kit-react ecosystem is under `@mysten/`), and no doc page indexes the dev-wallet helpers. Slot 3 UI mirrored `~/workspace/deepbook-sandbox/sandbox/dashboard/src/dapp-kit.ts` to find it. Recommendation: either promote the dev-wallet adapter into `@mysten/dapp-kit-react/dev` (where developers actually look) or document its incubation status prominently in the dapp-kit-react migration guide.

- **Pyth `PriceInfoObject` BCS layout is undocumented in `.sui-docs/`, `.move-book-docs/`, or any sandbox README** (`raw-friction.log` Cycle 4 review, `[deepbook]`/`[sui-sdk]`). The keeper reads price feeds by `sui_getObject` against the manifest's `pythOracles.deepPriceInfoObjectId` / `suiPriceInfoObjectId`, then decodes the returned BCS by hand (34 bytes, fixed offsets for `magnitude: i64` + `exponent: i32` + `timestamp_secs: u64`). The empirical capture lives in `independent/03-tpsl-vault/keeper/notes/pyth-shape.md` but a working-backwards layout is not how keeper authors should be discovering this. Recommendation: publish the canonical BCS layout for `pyth::price_info::PriceInfoObject` (and the embedded `PriceFeed` / `Price` structs) in the bundled `pyth` package's README, ideally with a TS reference decoder.

- **Move 2024 lint W99010 (`unnecessary 'entry' on a 'public' function`) is ambiguous when the spec mandates "entry function"** (`raw-friction.log` Cycle 2 review R4-003, `[move]`). The lint suggests removing `entry`, but in Slot 2 the spec wording explicitly used "entry function" because the wrapper is intended to be PTB-callable. Removing `entry` removes the PTB-callability guarantee even though `public` is sufficient at the language level. Recommendation: clarify in the lint message that `entry` carries semantic intent ("this is meant to be a PTB top-level call") even when it's redundant.

- **TypeScript LSP from a worktree-root cwd does not index sub-package `node_modules` cleanly** (`raw-friction.log` 2026-04-27T22:55:00Z, `[sui-sdk]`/`[forge-process]`). Across all 4 iterations of Cycle 1 + 2 iterations of Cycle 4 + Cycle 5, recurring stale `Cannot find module 'react'/'vitest'` diagnostics appeared in spec-defined IDE feedback even though `pnpm test` resolved cleanly inside each sub-package. This is partly forge-process noise (the worktree layout exacerbates it), but it has a real DeepBook DevX impact: a developer using a polyrepo or worktree layout will hit the same noise, and the natural reaction is to add per-package `tsconfig` paths or workspace `references` that don't help. Recommendation: ship a per-app `tsconfig.json` template that explicitly stops LSP module resolution at the sub-package boundary, and document the pattern.

## 3. What is not working / needs fix or refactoring

- **The sandbox indexer's `pools` postgres table is never populated by `pnpm deploy-all`, breaking ALL pool-keyed REST endpoints** (`raw-friction.log` 2026-04-27T21:25:00Z, `[sandbox]`/`[deepbook]`). Direct postgres inspection on a clean bootstrap shows the `pool_created` event table has 2 rows (DEEP/SUI + SUI/USDC) and `deepbook_pool_registered` has 1 row, but the `pools` table — read by `/get_pools`, `/orderbook/<name>`, `/trades/<name>`, `/ticker?pool_names=...` (verified in `external/deepbook/crates/server/src/reader.rs:181`) — has 0 rows. The `pools` schema requires curated metadata (`base_asset_symbol`, `base_asset_name`, `base_asset_decimals`) that is NOT present in the on-chain `pool_created` event, and nothing in the sandbox repo (`grep -rn "INSERT INTO pools" ./sandbox/` returns no results) populates it. Net effect: the entire indexer REST surface is non-functional out of the box, on a fresh sandbox, with default pools. This drove Slot 1 to rip out the planned indexer integration and read directly from on-chain BigVector slices — a ~10x scope expansion. **Recommended fix**: extend `scripts/utils/pool.ts::createDeepbookPools` to `INSERT INTO pools` after each on-chain pool creation, populating `base_asset_symbol/decimals/name` from `coin::CoinMetadata` (already published per the manifest) and `tick_size/lot_size/min_size` from the on-chain pool constructor args. Estimated 30-50 LOC.

- **`pnpm deploy-all` doesn't `docker compose down -v` first, leaving postgres state across deploys and silently desyncing the indexer cursor from a regenerated chain** (`raw-friction.log` 2026-04-27T20:55:00Z, `[sandbox]`). On the second-and-later runs, the indexer's `earliest_checkpoint` cursor has already advanced past where the new pools will be created on the regenerated chain (`FORCE_REGENESIS=true` is the default). The pool-creation event lands in the indexer's permanent blind spot, and `FIRST_CHECKPOINT=0` in `.env` is ignored because the postgres cursor says "already past that". The deploy script reports success; the user discovers the breakage only when they query the indexer. **Recommended fix**: prepend `docker compose down -v` (or, more conservatively, `docker exec deepbook-postgres psql -c 'TRUNCATE pools, pool_created, …'`) to `deploy-all.ts`'s Phase 1, and add a post-deploy gate that asserts `SELECT count(*) FROM pools = 2` (or whatever the manifest declares) before exiting.

- **`pnpm deploy-all` Phase 3 publish failures swallow the actual `sui client test-publish` error** (`raw-friction.log` 2026-04-27T19:42:00Z, `[sandbox]`). When the bundled `token` package fails to publish — observed during initial bootstrap because `sui::coin::create_currency` is deprecated and `#[allow(lint(share_owned))]` is an unknown warning category — the script prints "Failed to publish token" plus the build's deprecation warnings, but the actual transaction error never surfaces. The build output is misleading because the build itself succeeded; the failure is in the publish step. Required out-of-band invocation of `sui client test-publish` from inside the package directory to see the real error. **Recommended fix**: pipe `sui client test-publish` stderr through to the deploy-all output (or capture and re-emit on failure) instead of catching and discarding it. As a follow-up, fix the bundled `.external-packages/token/sources/deep.move` to use `coin_registry::new_currency_with_otw` (W04037) and a valid lint filter (W10007).

- **Pyth `:9010` is a status endpoint, not a price feed — keepers MUST read `PriceInfoObject` on chain** (`raw-friction.log` Cycle 1 review carry-forward, `[sandbox]`). The `faena.md` brief and the implicit design assumption was that Slot 3's keeper would HTTP-poll `:9010` for current prices. The endpoint actually serves only oracle-service metadata; price values live exclusively in the on-chain `pyth::price_info::PriceInfoObject` instances whose IDs are in `localnet.json::pythOracles`. The keeper had to add a `pythReader.ts` module that does `sui_getObject` + BCS decode every poll tick. The capability is there, but the assumption that an HTTP price feed exists wasted ~30 minutes during planning. **Recommended fix**: either rename the endpoint to `:9010/oracle-status` to make its purpose explicit, or actually expose `:9010/prices` (which the oracle-service already has the data for) so keepers have a documented HTTP fallback path.

- **Bundled `deepbook_margin/tests/helper/test_helpers.move:435` references an undefined symbol (`pyth::price_info::new_price_info_object_for_test`), breaking `sui move test` for any package depending on `deepbook_margin`** (`raw-friction.log` 2026-04-27T23:35:00Z, `[deepbook]`). The function is called by the bundled test helper but does NOT exist in the bundled `packages/pyth/sources/price_info.move`. Net effect: the canonical `example_contract` template — which the spec says to "mirror" for Move dependency declarations — itself can't `sui move test` clean against the bundled sandbox state. Both Slot 2 and Slot 3 Move packages had to explicitly drop the `deepbook_margin` dependency, with an explanatory comment, just to get green tests. **Recommended fix**: either add the missing test-only function to the bundled `pyth` package (`public fun new_price_info_object_for_test(price_info: PriceInfo, ctx: &mut TxContext): PriceInfoObject`), or strip the unused test helper. Either is a 5-LOC change.

- **DeepBook v3 `order_id` encoding is undocumented for SDK consumers and the bundled `chain-shape.md` prose is actively misleading** (`raw-friction.log` 2026-04-27T22:55:00Z, `[deepbook]`). The high bit (bit 127) is the ask flag (set for asks, clear for bids), the next 64 bits are the price, and the low 64 bits are an order-counter disambiguator. Captured chain examples: bid `12377783720203182843884075` → price `671000` (no inversion); ask `170141183460486719245069180370816077150` = 2^127 + (948000 << 64) + counter → masking bit 127, then `>>64`, yields `948000`. The `chain-shape.md` prose said "inverted for bids" — wrong. The correct decoder is identical for both sides: `(BigInt(orderId) & ((1n << 127n) - 1n)) >> 64n`. Slot 1 took 4 cycle iterations (bid-only, ask-broken structural fix that didn't wire through, etc.) to land this. **Recommended fix**: add a `decodeOrderId(orderId: bigint): { side: 'bid'|'ask', price: bigint, counter: bigint }` helper to `@mysten/deepbook-v3` and update `chain-shape.md` with empirically-verified examples for both sides.

- **`suix_queryEvents` `MoveModule` filter selects on `transactionModule` (where the event was emitted from), not on the event struct's declaring module** (`raw-friction.log` 2026-04-27T21:47:00Z, `[sui-sdk]`). Filtering on `module: "order_info"` returns zero events even though the event-type symbol is `0x...::order_info::OrderInfo`. Slot 1 must filter on `module: "pool"` for any DeepBook event read; Slot 3's keeper must filter on `module: "tpsl_vault"`. Not documented in the `@mysten/sui` 2.x event-fetching docs we consulted. **Recommended fix**: rename the SDK filter to `EmitterModule` (or document that `MoveModule` means "the module that emitted, not the module that declared the event type") and add an explicit example in `.ts-sdk-docs/`.

- **Move test_scenario CLEARS the event buffer on every `next_tx`**, undocumented and surfaces as test failures only at the third call (`raw-friction.log` 2026-04-28T00:30:00Z, `[move]`). `event::events_by_type<>()` only sees events emitted in the current tx. Tests that emit an event in tx N and want to inspect it must do so BEFORE calling `next_tx`. Cycle 3 iter-1 was bitten by 4 of 7 tests failing on `events.length() == 1` after the tx that emitted them. Not documented in `.move-book-docs/book/testing/test-scenario.md`; only callable from `test_scenario_tests.move:1092` (`assert_eq!(event::num_events(), 0)` after `next_tx`). **Recommended fix**: document the cross-tx event semantics prominently in the test-scenario doc, ideally with a contrasted example pair (correct/incorrect placement of the event assert).

- **Move test_scenario's shared-object store does not fully reset between two `begin/end` pairs in one test function, breaking spec-mandated boundary tests** (`raw-friction.log` 2026-04-27T23:55:00Z, `[move]`). Calling `setup_everything` a second time (as Slot 2's T-003 did) tries to create Registry and other objects whose `versioned::create` dynamic-field-add fails with `EFieldAlreadyExists` because the first scenario's objects (same UID, due to counter reset at `begin`) are still in the global test VM store. T-003 (`swap_succeeds_when_min_out_equals_realised` boundary) was structurally unpassable in a two-scenario pattern within one test function and had to be amended out — **leaving the `>=` → `>` regression silently uncovered** by Slot 2's test suite. **Recommended fix**: either reset the shared-object store on `end()`, or document this constraint in `.move-book-docs/book/testing/test-scenario.md` with a "one scenario per `#[test]` function" rule and a recommended pattern for parameterised boundary tests.

- **The `[environments]` requirement on Move 2024 1.69.x consumers has no `localnet` option until you write one yourself, and the chain-id value is a stale-by-design constant** (`raw-friction.log` 2026-04-27T23:35:00Z, `[move]`). Build/test fail with "Could not determine the correct dependencies to use for `localnet`; pass one of `--build-env testnet` or `--build-env mainnet`" — but neither is what we want. Resolution that worked for Cycle 2: declare `[environments]\nlocalnet = "a62c4e17"` in the consuming package's `Move.toml` and invoke `sui move test --build-env localnet`. The chain-id value need not match the running sandbox's chain identifier for `sui move build`/`test` (which doesn't talk to a node), only for `sui client publish` — but `pnpm deploy-all` regenerates the chain ID on every run, so the value in `Move.toml` is stale-by-design for any publish workflow. **Recommended fix**: either auto-detect localnet (the CLI already knows the active env via `sui client active-env`) or have `pnpm deploy-all` write the current chain ID into a sandbox-published `Move.toml.localnet.fragment` that consumers can `include` from their own `Move.toml`.

- **DeepBook v3 silent no-op when `base_quantity < min_size` after lot-size rounding** (`raw-friction.log` Cycle 2 review medium #3, `[deepbook]`). `pool.move:385-387` returns input coins unchanged with `quote_out.value() == 0` rather than aborting. Slot 2's wrapper aborts with `EInsufficientOutput` for any `min_out > 0` — conflating "swap effectively no-op'd due to lot-size rounding" with "slippage floor breach". For `min_out = 0`, this path silently SUCCEEDS as a no-op, returning the user's inputs. A consumer expecting a revert on undersized swap is going to silently lose to bug-classes that look like nothing happened. **Recommended fix**: have DeepBook abort with a distinct `ESwapBelowMinSize` rather than returning a zero-value quote coin, OR document the no-op behavior in a top-of-file comment and recommend wrappers add a pre-check.

- **`BalanceManager` is `key + store` but the dashboard pattern stores it as a shared object referenced by ID — wrap-vs-reference choice is undocumented** (`raw-friction.log` faena.md §10 risk row, `[deepbook]`). Slot 3 spent design time on whether the vault should own the `BalanceManager` (matching the `key + store` ability set) or reference one by ID (matching the dashboard's `action-cards.tsx` pattern). The DeepBook v3 docs in `.sui-docs/onchain-finance/deepbookv3/contract-information/balance-manager.mdx` describe the type but not the pattern. Slot 3 ended up using the no-manager swap path entirely to sidestep the question, but a real composed protocol can't avoid it. **Recommended fix**: publish a "BalanceManager: own vs reference" decision matrix in the DeepBook docs, with concrete examples from both patterns and the trade-offs (shared-object congestion vs ergonomics, who pays gas for `register_balance_manager`, etc.).

- **`min_quote_out = 0` disables DeepBook's `EMinimumQuantityOutNotMet` slippage guard, which is correct-by-design but creates an MEV gap** (`raw-friction.log` Cycle 3 review medium #1, `[deepbook]`). Slot 3's `execute_trigger` deliberately passes `min_quote_out = 0` because the TP/SL condition gate IS the slippage gate from the user's perspective. But MEV bots can manipulate the DeepBook order book between the keeper's price-read and the on-chain swap's execution and extract value, since DeepBook itself isn't checking. This is a load-bearing design observation: any keeper-driven trigger pattern needs defense-in-depth (e.g., compute `min_quote_out = current_price * 0.95`) and DeepBook's `min_out=0` semantics make this the consumer's responsibility, not DeepBook's. **Recommendation**: document the keeper-trigger MEV pattern explicitly in the DeepBook v3 design notes, with a recommended slippage-floor formula tied to `current_price`.

- **`@mysten/deepbook-v3` SDK was deliberately NOT used in this evaluation, and the reason matters** (`raw-friction.log` 2026-04-27T21:25:00Z + Cycle 1 carry-forward #2-#3, `[deepbook]`). The plan was to use it for indexer access in Slot 1 and for swap construction in Slot 3 — both got dropped. Slot 1 dropped it because the indexer surface it wraps was non-functional out of the box (see finding #1 above) and chain-direct reads were the only path forward. Slot 3 dropped it because the keeper builds the `execute_trigger` PTB by hand against the wrapper Move contract, not against `pool::swap_exact_base_for_quote` directly — the SDK's swap helper would have wrapped the wrong layer. Net effect: across three apps that are explicitly DeepBook integrations, we exercised zero of the `@mysten/deepbook-v3` SDK surface. That is a real signal — the SDK didn't fit either of the natural use cases without significant friction. **Recommendation**: verify the SDK's indexer-bound code paths against the actual sandbox indexer state (not the testnet/mainnet state), and add explicit SDK docs for "I am building a Move contract that wraps DeepBook — what TS shape do you give me?"

- **No reference indexer-consuming dashboard pattern exists in the sandbox to mirror for Slot-1-class apps** (`raw-friction.log` Cycle 1 review carry-forward #4, `[sandbox]`). The sandbox dashboard at `~/workspace/deepbook-sandbox/sandbox/dashboard/` consumes the indexer for the `/health` route only (a handful of HTTP probes) and reads everything else either chain-direct or from the manifest. There is no proven-against-the-sandbox example of "render a market-stats view from the indexer's `/orderbook` + `/trades` + `/ticker` surface" — even though that's the apparent target use case for the indexer's existence. Slot 1 was greenfield against the sandbox in this respect. **Recommendation**: add a `dashboard/src/routes/market-stats/` route that exercises the indexer's pool-keyed REST surface end-to-end. Doing so would surface (and force a fix to) finding #1 above, since the route would be unable to render against a fresh sandbox.
